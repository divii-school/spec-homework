## Notes

- **Round 1 and Round 2 written together**: Because Round 1 was overdue and Round 2 was announced the same day, I wrote both rounds in a single pass and documented the changes in the change log (v1.0 → v1.1). The v1.1 entry lists every ID that was added or modified for the paid plan.
- **Design decisions I made** (not given in the brief): free tier limit (3/month), ATS scoring dimensions and weights (7 dimensions totalling 100), max file size (5 MB), data retention (90 days), AI provider (OpenAI GPT-4o), file storage (AWS S3; upload through the API, presigned URLs for download only — fixed in v1.2), PDF generation (Puppeteer + Handlebars), currency storage (paise to avoid float errors).
- **v1.2 (Oct 28) — what the build test taught me**: the builder logged 18 guesses, most from three gaps: (1) I described analysis as both synchronous (API-005 returned 200 inline) and queued (FR-017 "re-queues", FR-010 "async via queue") without ever defining the queue; (2) CMP-004 said "presigned URLs for upload" while Flow 1 and API-001 used multipart through the API; (3) FR-011 said "the user's tier changes" but no table or column held a tier, nothing said how it expired, and `GET /analyses/compare` was not actually gated. Fix: one explicit decision per gap, recorded in a new §4.6 decisions table (D-01..D-03) and referenced from every affected ID. Lesson: when a spec mentions a mechanism (queue, cache, tier) it must have a home — a component ID, a table/column or a key name — or the builder will invent one.
- **Commit cadence**: round 1 + 2 landed in one push on Oct 22, which the reviewer flagged. From v1.2 on, changes are committed in small steps (the spec revision and the process notes as separate commits, further revisions per decision) so the history shows the work. v1.2 was prepared on branch `spec/sovan-v1.2` while `spec.md` was frozen for scoring, and merged only after the freeze was lifted.
- **What I checked by hand**: cross-referenced every FR-ID in the traceability matrix against the requirements table to ensure no orphaned IDs. Verified every API endpoint references a valid FR. Checked every DB column referenced in API responses exists in the ERD. Confirmed dimension weights sum to 100 (10+15+20+20+10+15+10).
- **v1.3 (Oct 30) — what the second build test taught me**: 83 guesses on v1.2 even after fixing the three reviewer points, because the same numbers were written in up to nine places and the payment flow only described the happy path. The two cheapest fixes were structural, not textual: a constants table (§3.4) referenced by name, and one lifecycle section (§5.6) that every API points at instead of each API re-describing events. Second lesson: whenever two components could both write a column (`expires_at`, `attempts`, `current_period_end`) the spec must name the single owner, or the builder invents one.
- **Facts checked by hand on 2026-10-30 (PLAYBOOK step 7)**: Razorpay webhook headers are `X-Razorpay-Signature` (HMAC-SHA256 of the raw body) and `x-razorpay-event-id` (unique per event, recommended for de-duplication); Razorpay states events may arrive more than once and not in order; the subscription event list is `authenticated / activated / charged / completed / updated / pending / halted / cancelled / paused / resumed`; payloads carry `current_start`, `current_end`, `charge_at`, `status`, `paid_count`. **Not published**: the webhook retry window — the earlier "retries for 24 h" line in §4.4 was an AI guess and is now marked unverified; the design assumes duplicates and late events instead. BullMQ 5 has no per-job timeout option (the spec's old "job timeout 90 s" was wrong); the processor now aborts the OpenAI call itself.
- **Decisions I made in v1.3** (recorded as A-06..A-11, K-28..K-31, D-04): checkout TTL 24 h, renewal grace 120 h (eNACH can take two working days), stalled-job timeout 5 min, max 3 manual retries, ownership mismatch answered 404, refunds never change the tier automatically, erasure keeps pseudonymised financial records for 7 years, frontend on AWS Amplify with a 401 → platform-login contract.
- **AI limitations**: Claude generated the initial structure but I reviewed and adjusted: (a) added magic bytes validation for file uploads (AI initially only checked MIME type), (b) added the partial unique index on subscriptions to prevent double-active subscriptions, (c) specified `forbidNonWhitelisted: true` on ValidationPipe (AI defaulted to just `whitelist`).
