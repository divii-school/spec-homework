## Notes
Anything worth knowing about how you worked: decisions you changed, things the AI got wrong, what you checked by hand.

- 2026-10-19: Fixed the core design decisions before writing (Spring Boot 3 / Java 21, Claude API for scoring, S3 in ap-south-1 for DPDP, 5 MB / 5-page limit, FREE 3 analyses and 3 suggestions per month, PREMIUM 50 and all, 30-day file retention, 180-day result retention). Then wrote sections 1–3 so that every later section can trace back to an ID.
- 2026-10-20: Sections 4 (architecture) and 5 (database). Checked the AI call against the current Anthropic API reference: current Claude models reject forced `tool_choice` and do not accept `temperature`, so the spec uses structured outputs (`output_config.format`) and A-9 was corrected. Their reasoning counts towards `max_tokens`, so NFR-015 went from 4,000 to 8,000. Designing the sweeper showed that FR-008 had no end state for a message lost twice; added it to criterion 7. Tested the four redaction regexes against sample phone, email and URL formats (the first phone pattern left a stray `(` on `(080) 2345 6789`, fixed), and parsed all 8 Mermaid diagrams with Mermaid 11 before committing.
- 2026-10-22: Sections 6 (API design) and 7 (traceability). Wrote the common rules first (check order, request and response rules, pagination, the `details` shape per error code) so each endpoint only lists its own checks. Writing the endpoints exposed three contradictions in sections 1–4, fixed at the source rather than worked around in section 6: CR-014 said a wrong body value is 400 while FR-006 returns 404 for an unknown `resumeId`; the `resetAt` example in 1.4 used `+05:30` although CR-025 says every timestamp is UTC; and `details.resetAt` pointed into a field defined as an array. Added API-016 (consent status), because without it the UI could not know whether to show the notice. Checked by script that every API, CMP, TBL, FR and NFR id referenced is defined, that every error code used in the text is in 6.3, and that all 41 FR/NFR rows are in the matrix.
- 2026-10-25: Round 2, the Resume Pro change (₹299/month via Razorpay, unlimited analyses, all suggestions, history and comparison, cancel to the end of the paid month, FREE unchanged). Decisions fixed before editing, each written into the spec with its reason: the module bills through Razorpay Subscriptions and owns the plan (A-11), so the token's `plan` claim and my round-1 `PREMIUM` plan are deprecated instead of kept beside `PRO` (A-2, A-3); Pro access is the single rule `access_until > now`, which covers cancellation, failed renewals and halted subscriptions alike (FR-025, A-16); "paid month" means Razorpay's billing cycle, not the calendar month. One conflict inside the change request itself: my round-1 spec already gives every user a history list (FR-014), and rule 5 says FREE must not change, so FREE keeps that list and Pro history adds filters, dimension scores and the comparison (FR-026, FR-027). Erasure had to change too: an active subscription must be cancelled at Razorpay or the user would keep being charged after deleting their data, so erasure cancels it immediately through a retry table (FR-019 criterion 7, TBL-019). No ID was renumbered. Removed rules are marked Deprecated. Checked by script that every referenced CR/FR/NFR/CMP/TBL/API/ERR/A id is defined (33 CR, 30 FR, 21 NFR, 22 CMP, 19 TBL, 22 API, 25 ERR), that all 51 FR/NFR rows are in the matrix, and that all 12 Mermaid diagrams parse with Mermaid 11 (one failed first: a `;` inside a sequence message ends the statement). Example Unix timestamps in the Razorpay payloads were converted and checked against the ISO dates used beside them. A separate build-test agent then read only this spec and logged 4 guesses and 7 contradictions in the new parts. The most serious was that the V3 migration updated `PREMIUM` rows to `PRO` while the old CHECK still allowed only `FREE`/`PREMIUM`, so it would have failed on dev data. The rest were a missing Pro-page state for a failing renewal, consent withdrawal cancelling a paid plan against my own A-14, the undefined fake Razorpay client, and smaller wording conflicts. All were fixed and listed in the v0.4 change-log row, and the checks were re-run clean.

- 2026-10-26: Second build test before the scored one. A separate Claude Code agent read only v0.5 and listed 5 guesses and 4 contradictions, none of them high. Fixed by letting Razorpay's fetched status decide before any local expiry, plus a backstop that cancels at Razorpay any subscription that shows signs of life after it is terminal locally (FR-029 criterion 9, new TBL-019 reason `ORPHANED`, added to V3 because V3 is unreleased). The rest were wording: CR-033 implied a 401 for a bad checkout signature where API-018 says 400; the cancel response for an unpaid subscription; a missing Pro page state for `ACTIVE` with plan `FREE`; two meanings of "open subscription"; an alert that would have fired on every abandoned checkout; the webhook `outcome` of a skipped event; where the environment name comes from (`APP_ENV`); and the source of the Pro history filter options. Checked each finding against the text before changing it, then re-ran the ID and Mermaid checks. Change log v0.6.
