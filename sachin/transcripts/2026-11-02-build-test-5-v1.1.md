I walked the full build: Flyway V1–V3 and the grants, all 22 endpoints, the worker, sweeper, retention, billing jobs and AI call, the frontend pages and 401 handling, Razorpay checkout, verification, webhooks and reconciliation, the per-environment config, and the pipeline and Terraform. Only six places would force a guess or carry a real disagreement, and none of them is high impact.

**Gaps, highest impact first**

1. **4.3.3 / 4.2 (CMP-010 vs CMP-011) / 4.6.1 / 4.6.4 — GUESS (medium).** It is unclear which component owns the "more than half of the suggestions dropped" retry, and what the retry budget is.
   - 4.3.3 says the check makes the response "count as `AI_INVALID_RESPONSE` and is retried like one".
   - But the diagram retries inside the AI client, then hands over: "AI-->>W: validated result; W->>W: … suggestion checks and ranking".
   - The substring check needs the redacted text, and 4.6.1 says that text "is not stored".
   - 4.6.4 drops suggestions over the length limits in CMP-011, so the "half dropped" count is split across two components.
   - If the worker calls `analyse()` again, the client's own retry could make 4 provider calls (about 184 s), which runs past the 120 s stuck-running sweeper.
   - Fix: CMP-011 runs every suggestion check (lengths, substring, placeholder) on the redacted text it built, decides the single retry itself (at most 2 provider calls), and returns the redacted text or line positions with the result.

2. **FR-008 c3 / 4.3.3 / 4.4 — GUESS (medium-low).** Connection-level failures to Anthropic are not classified. That covers connection refused, DNS failure, TLS errors and connection reset.
   - FR-008 c3 retries only "timeout, HTTP 429/5xx or an invalid response". 4.3.3 says only that "a 4xx other than 429" is not retried.
   - Whether these failures are retried, and which `failure_reason` they get (`AI_TIMEOUT` or `AI_PROVIDER_ERROR`), is not stated.
   - Fix: treat them like 5xx — retried once after 2 s, then `AI_PROVIDER_ERROR`.

3. **4.3.6 cancellation-retry table vs 4.8.7 `RazorpayCancellationOverdue` — CONTRADICTION (low-medium).** A harmless case can page someone in prod.
   - The table says `created` is "done if the fetched `expire_by` has passed, else retried at the next run".
   - `expire_by` can be up to 24 h after the TBL-019 row is written (erasure right after starting a checkout). The job runs only every 10 min, so the row can stay more than 24 h old for up to 10 minutes.
   - The alert is "> 0 in 5 consecutive 1-minute periods", severity critical, so prod would page for an expired, unpayable checkout. That contradicts the table's own note that only `authenticated/active/pending` should page ("which is intended").
   - Fix: set `next_attempt_at` = `expire_by` + 1 min for a fetched `created`, or leave such rows out of `CancellationOverdue`.

4. **4.3.9 "Razorpay fetched status → local effect" — GUESS (low).** The table has no row for `paused` (or any other status).
   - 3.3 lists "pausing or resuming" as out of scope and ignores those events. But support can pause a subscription in the dashboard.
   - Reconciliation, verification and the expiry fetch would then receive a status the table does not cover.
   - Fix: add a row "`paused` or any unlisted status: row unchanged, ERROR `billing.unknown_status`, not a fix; verification answers 202".

5. **4.4 `FakeRazorpayClient` — GUESS (low; affects local and the CI Playwright run).** The fake's semantics after `cancel` are unclear.
   - The spec says "`fetch` returns `active` …" and "`cancel` … marks the stored subscription `cancelled`".
   - It does not say whether `fetch` then returns `cancelled`, or whether `cancel_at_cycle_end: 1` also marks it cancelled at once. That second case would make local reconciliation end a cycle-end cancel early, against FR-028 c2.
   - Also, "fetch returns `active`" means the 03:00 reconciliation turns every abandoned local checkout into `PRO`.
   - Fix: `fetch` returns the stored status (`active` after the first verification fetch, `cancelled` only after `cancel_at_cycle_end: 0`, `active` plus a cancelling flag otherwise), and an unpaid checkout stays `created`.

6. **4.8.2 local column vs 4.8.2 "Local stack" / 1.7 / 2.2 — CONTRADICTION (low).** Two cells assume the API runs in the API repo's compose file.
   - The `APP_MODE` cell says "`api` (`worker`, `migrate` in those compose services)".
   - The `JAVA_TOOL_OPTIONS` cell says "in compose `-XX:MaxRAMPercentage=75 -javaagent:…`".
   - But "Local stack" says "Nothing else: the API, the worker and the migration run on the host with `scripts/run-local.sh`", and 1.7 says "postgres, redis and LocalStack only".
   - Fix: change both cells to "in the web repo's `e2e/docker-compose.yml` services (4.8.4)".
