## Final report

Build test of `sachin/spec.md` (v1.2). I read all 3,344 lines in chunks, opened no other file, edited nothing and used no git.

**Verdict:** I could build the whole system from this spec without asking anyone. Database, APIs, worker and AI call, Razorpay, config for every environment and deployment are all specified down to SQL, headers, ports and IAM. I found one real contradiction (in the Pro page states) and one alert rule that would page the on-call wrongly. Everything else is low-impact.

### Gaps, highest impact first

1. **FR-030 criterion 3, states (b) and (c) — CONTRADICTION (medium).**
   - The states are "decided in this order": "(b) plan `PRO` and `cancelAtPeriodEnd` false: … the next charge date and 'Cancel'", then "(c) plan `PRO` and cancelling or `CANCELLED`: 'Cancelled: Pro ends on …', no buttons".
   - A `CANCELLED` row with access left always has `cancel_at_period_end = false`. This happens when support cancels in the Razorpay dashboard (3.3 says this is "handled like a user cancellation"), or when reconciliation fetches `cancelled`.
   - Such a row therefore matches (b) first. The page offers "Cancel" and a next-charge line that is null, and state (c) is never reached for `CANCELLED`.
   - Fix: make (b) "plan `PRO`, `status = ACTIVE` and `cancelAtPeriodEnd` false", or evaluate (c) before (b).

2. **4.8.7 `Api5xxRateHigh` against 6.1 / ERR-025 / ERR-026 — GUESS (medium).**
   - The critical alert counts every `status=~"5.."` response.
   - 6.1 says the module returns 503 on purpose for `PAYMENT_PROVIDER_UNAVAILABLE` and `SERVER_BUSY`.
   - So a Razorpay outage, or a burst of uploads while the server is busy, pages PagerDuty in prod as an API failure. It also overlaps the separate warning `RazorpayCallFailureRateHigh`.
   - Fix: exclude handled 503s (filter on `api_errors_total{code!~"PAYMENT_PROVIDER_UNAVAILABLE|SERVER_BUSY"}` or `status!="503"`), or state that paging on them is intended.

3. **FR-028 criterion 9 against FR-030 states (a) and (a2) — GUESS (low–medium).**
   - The confirm dialog text is "You keep Pro until <accessUntil> and will not be charged again."
   - "Cancel" is also offered in state (a) (`AUTHENTICATED`/`PENDING`, "plan may be FREE") and in state (a2) (`ACTIVE` with plan `FREE`).
   - In both, the subscription view's `accessUntil` is null ("`null` when `FREE`"), and in (a) the user does not keep Pro at all.
   - Fix: add a second dialog text for `accessUntil = null` / immediate cancellation.

4. **FR-013 criterion 4 against NFR-003 and FR-008 criterion 7 — GUESS (low–medium).**
   - The UI "stops after 150 s with a 'taking longer than expected' message".
   - An analysis may legitimately stay `QUEUED` for "about 10 minutes" (5 min, one re-queue, 5 min more).
   - Nothing says whether the page offers "check again", polls more slowly, or only refreshes on a manual reload. Without one of those, the user never sees the late result or the `FAILED` reason.
   - Fix: specify the behaviour after 150 s, e.g. a "Check again" button or polling every 30 s until a terminal status.

5. **3.4 and FR-016 criterion 2: labels for enum codes and inline texts — GUESS (low).**
   - 3.4 has keys only for error codes, failure reasons, Pro benefits and categories.
   - It has no keys for dimension names, experience levels (`MID (3–6 years)`), bands, severities, importance, analysis statuses, the upgrade banner, or the inline FR texts. Those inline texts are FR-013 "taking longer…", FR-023's two texts, FR-024 criterion 8, FR-027 criterion 6, the FR-030 state texts, CR-035's message and button, and the checkout-script failure text.
   - The PDF template has no product name, section headings or dimension labels, although FR-016 criterion 2 requires a "product name".
   - Fix: add these keys and texts to 3.4, plus the PDF label set.

6. **FR-010 / FR-011 criterion 4 / 4.3.3: duplicate AI output — GUESS (low).**
   - Ranking is "severity, then the line's position (offset)". It is not defined which occurrence's offset is used for a repeated line, nor how two suggestions on the same line with the same severity are ordered.
   - Duplicate missing-skill names (e.g. "Docker" and "docker") both pass the case-insensitive filter and would be stored twice.
   - Fix: offset = first occurrence; tie-break = AI order; deduplicate missing skills case-insensitively before assigning positions.

7. **4.6.4 `FakeAiClient` — GUESS (low).**
   - It makes "one suggestion per line among the first 5 non-empty lines", with the rewrite being the line prefixed by "Delivered: ".
   - Resume header lines usually carry `[EMAIL]`/`[PHONE]`/`[URL]` after redaction. Those suggestions are dropped (FR-011 criterion 5), and if 3 of the 5 are dropped the "more than half" rule makes every local, e2e and staging load-test analysis `AI_INVALID_RESPONSE`.
   - It is also not stated whether the fake reads the redacted text.
   - Fix: the fake takes the first 5 non-empty lines of the redacted text that contain no placeholder.

8. **NFR-015 against FR-004 and A-4 — CONTRADICTION (low).**
   - NFR-015 sets "Input ≤ 12,000 tokens".
   - Text up to 30,000 code points is accepted, and non-English resumes "are still processed". A 30,000-character non-Latin resume exceeds 12,000 tokens, and nothing enforces the cap.
   - Fix: either count tokens before the call and reject or fail beyond the cap, or reword NFR-015 as an English-text estimate only.

9. **4.8.7 / NFR-013 / NFR-020: metric label values — GUESS (low).**
   - "Every counter … registered at 0 … for each label value listed", but some values are never listed:
     - `ai_tokens_total{type}`
     - `razorpay_webhook_events_total{type}`
   - `billing_activation_seconds{path}` allows only `verification`, `webhook` and `reconciliation`. The FR-024 criterion 3 expiry fetch in API-017 can also be the first path to raise `access_until`, and it has no label.
   - Fix: list the label values (`input`/`output`, the 7 event types plus `unknown`) and add `path="checkout_expiry_fetch"` or say it is folded into `reconciliation`.

10. **CR-016 / CR-037 / 4.8.3: page security headers — GUESS (low).**
    - Only HSTS and `Cache-Control` are specified for pages. There is no CSP or frame-ancestors / X-Frame-Options.
    - The Pro page loads `checkout.js` and Razorpay's iframe, and the privacy page holds the one-click erasure, so the builder must invent a policy (or none).
    - Fix: state the CSP (allow `checkout.razorpay.com` and the API origin) and `frame-ancestors 'none'`, set in the middleware.

11. **CR-001 / CR-035 / A-18: token lifetime — GUESS (low).**
    - The module never refreshes tokens, and every 401 does a full-page redirect.
    - 4.5 implies roughly 15-minute tokens ("no 15-minute token delay"), but no lifetime is stated. A-18 also does not say whether the login page returns a still-signed-in user to `returnTo` silently.
    - A user mid-checkout or mid-upload could be bounced. This changes the API client (silent refresh versus redirect).
    - Fix: state the token lifetime and that the platform login page auto-redirects an already signed-in user; or add a platform refresh call.

12. **4.6.2 / 2.2: prompt file selection — GUESS (low).**
    - `prompt_version` is "the prompt file name" and "a prompt change is a new file".
    - Nothing in 4.7 says which file is active when `analysis-v1.txt` and `analysis-v2.txt` both exist.
    - Fix: add `app.ai.prompt-version` (default `analysis-v1`) that names the file.

**Total: 12** (2 contradictions, 10 guesses). None is high; items 1–2 are medium, the rest low or low–medium.
