## Final report

Build test of `sachin/spec.md` (v0.7). I read the whole file (3,166 lines) and opened nothing else in `spec-homework`. I edited no files and used no git.

Overall the spec is very complete. Every endpoint has its check order, errors and wire shape, the database has all columns and constraints, the AI request, schema and validation are given, Razorpay has its flows and state rules, and every environment and deploy step is written down. What is left is mostly edge behaviour. Ordered by impact, highest first:

1. **FR-008 criterion 1 vs criterion 7 / 4.2 diagram / 4.3.4. CONTRADICTION.** Criterion 1 says "Status moves only `QUEUED → RUNNING → COMPLETED` or `QUEUED → RUNNING → FAILED`; any other transition is rejected in code". But criterion 7, the 4.2 diagram ("QUEUED --> FAILED: still queued 5 min after the one re-queue") and the 4.3.4 "Lost twice" rule all need `QUEUED → FAILED`. A guard built from criterion 1 blocks the sweeper. *Fix:* add "or `QUEUED → FAILED` (sweeper only, AI_TIMEOUT)" to criterion 1.

2. **4.3.9 / FR-029 criterion 8 / 4.3.8: `last_event_at` after verification or reconciliation. GUESS.** `last_event_at` is written only "when a status change is applied" by an event. Verification and reconciliation change `status` but do not set it. So a stale event that Razorpay redelivers later (for example a `pending` created before a charge that reconciliation already applied) is newer than `last_event_at` and moves the row back to `PENDING`. The Pro page then shows state (a) with "Cancel", and FR-028 criterion 3 cancels that paid subscription immediately (`cancel_at_cycle_end` 0). *Fix:* when verification or reconciliation changes `status`, set `last_event_at` to the fetch time, and skip events older than it.

3. **4.8.2 / 4.8.7 / 4: what the `worker` mode starts. GUESS.** The worker must serve `/actuator/prometheus` on 8081 for the sidecar. But 4.8.2 gives `PLATFORM_JWKS_URL`, `PLATFORM_ISSUER`, `CORS_ALLOWED_ORIGINS` and `RAZORPAY_WEBHOOK_SECRET` to `api` only. The spec never says whether the worker listens on 8080, or which controllers, filters and security beans load per `APP_MODE`. *Fix:* state that the worker runs only the management server, and list the bean groups (and their conditions) per mode.

4. **4.8.2 "Where values come from": host run of the API locally. GUESS.** Non-secret local values (`APP_ENV`, `CORS_ALLOWED_ORIGINS`, `PLATFORM_ISSUER`, …) are said to live in `docker-compose.yml`, and secrets in `.env`. The local column, though, is "for the API run on the host (`./mvnw spring-boot:run`)". Spring Boot reads neither file on a host run, and `APP_ENV` is required. *Fix:* put every local value in `.env.example` and load it with `spring.config.import=optional:file:.env[.properties]` (or a named equivalent).

5. **4.4 Razorpay row / CMP-021: cancellation retry after a 4xx. GUESS.** The spec says "on a 4xx the job fetches the subscription and treats `cancelled`, `completed` or `expired` as done". Nothing covers a fetch that returns `created` (an erased `CREATED` checkout, which 4.3.6 cancels too), `halted` or `pending`. The row would be retried forever, and the critical `RazorpayCancellationOverdue` alert pages after 24 h. *Fix:* define the outcome for each fetched status (for example `created` past `expire_by` counts as done; otherwise retry with an attempts cap and a warning).

6. **NFR-006 / NFR-001 vs 4.7 / 4.8.2: staging load tests. GUESS.** NFR-006 asks for "Load test on staging with the fake AI client and 2 s simulated latency". But `app.ai.fake-latency` (4.6.4) has no env variable and is not in the 4.7 table. 4.8.2 leaves staging `AI_PROVIDER` at its `anthropic` default with no override path. The k6 tests at 20 req/s also need at least 20 user tokens (60 req/min per user), and staging tokens come only from the platform login. *Fix:* add `AI_FAKE_LATENCY` plus a documented staging load-test override, and name the k6 token source (for example platform test accounts or service-minted tokens).

7. **4.4 / 4.8.6 HikariCP sizes per mode. GUESS.** The pool is 20 per API task, 10 per worker task, and at most 2 for migration, but there is no property or env-var row for it in 4.7 or 4.8.2 ("one row per environment variable of every service"). Profiles follow `APP_ENV`, not `APP_MODE`, so `application-<env>.yml` cannot set it per mode. *Fix:* add a `DB_POOL_SIZE` row with a value per service, or make the default keyed on `app.mode`.

8. **FR-030 criterion 3 vs FR-029 criterion 9 / glossary "current subscription": PRO with `subscription: null`. GUESS.** An `EXPIRED`/`ORPHANED` row whose `access_until` is raised by a late charge gives plan `PRO`. That row is not a "current subscription", so `subscription` is `null`. State (b) ("plan `PRO` and `cancelAtPeriodEnd` false … and Cancel") then has no subscription to read, and its Cancel button gets a 404. *Fix:* add a state for "PRO, no current subscription": "Resume Pro until <accessUntil>", no buttons.

9. **FR-001 / A-14: notice content. GUESS.** The notice must name a "grievance contact" and the Pro page shows a "short payment notice". Neither text nor the contact details are given; the UI only shows them "from its message files". A builder cannot invent a grievance officer. *Fix:* attach the notice text (or `messages/en.json` keys and values) with the grievance contact.

10. **FR-022 / 2.2 frontend tree: admin screen. GUESS.** FR-022 says "An admin sees aggregated usage", but no admin page appears in the 2.2 tree or in CMP-001, and the Grafana dashboard does not use API-015. *Fix:* state "API-015 only, no UI", or add `src/app/admin/page.tsx`.

11. **NFR-003 vs FR-008 criteria 6–7 / 4.3.4. CONTRADICTION.** NFR-003 measures "from `QUEUED` to `COMPLETED` … hard limit 120 s, then `FAILED` (FR-008)". The sweeper's 120 s counts from `started_at`, and a `QUEUED` analysis may wait 5 + 5 minutes. *Fix:* reword to "120 s after `RUNNING` starts; at most about 10 min in `QUEUED`".

12. **FR-011 criterion 3 vs 4.3.3 / 4.6.1 / TBL-009. CONTRADICTION.** FR-011 says "The original line must appear in the extracted text". 4.3.3 says "in the text sent", 4.6.1 says "Suggestion checks (4.3.3) compare against it" (the redacted text), and TBL-009 says "as sent to the AI (redacted placeholders may appear)". It is also unclear whether "appear" means a substring or a whole line. *Fix:* FR-011 should say "the redacted text sent, as a substring after normalisation".

13. **4.3.1 vs TBL-005: text length unit. CONTRADICTION.** 4.3.1 defines "`text_length` is `String.length()`" (UTF-16 units), but `ck_resume_text_text` uses `char_length(text) BETWEEN 300 AND 30000` (code points). Text with emoji or other supplementary characters can pass in Java and fail the CHECK, giving a 500 instead of a 422. *Fix:* use `codePointCount` in Java (or `octet`-neutral wording in both places).

14. **FR-008 criteria 3–4 / 4.6.4: two different failures. GUESS.** The spec does not say which `failureReason` is stored when the two attempts fail differently (for example a timeout, then an invalid response). It also does not say whether `input_tokens` and `output_tokens` add up both attempts. *Fix:* use the last attempt's reason, and sum the tokens.

15. **TBL-011 vs 4.3.6: `db_completed_at`. CONTRADICTION.** TBL-011 makes it `NOT NULL`, "commit time of the deleting transaction". 4.3.6 shows "COMMIT, set db_completed_at", which is after the commit, when the row must already hold a value. *Fix:* "set to `clock_timestamp()` by the last statement before COMMIT".

16. **4.3.1: extractor thread pool. GUESS.** The pool is "a bounded pool of 4 threads per API task", but what happens when it is saturated (queue length, wait time, or reject and with which code) is not said. *Fix:* give the queue size, the maximum wait, and the error code on overflow (for example 500 `INTERNAL_ERROR`).

**Total: 16 items. 5 contradictions (1, 11, 12, 13, 15) and 11 guesses (2–10, 14, 16).** None of them blocks the main FREE flow. The two with money or correctness risk are 1 (the status guard blocks a required path) and 2 (a paid subscription can be cancelled by mistake).
