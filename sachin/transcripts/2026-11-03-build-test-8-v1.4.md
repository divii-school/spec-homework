## Final report

I read the whole spec (`spec.md`, 3,422 lines, v1.4) and nothing else. I searched the file for an answer before listing each item; anything the spec settles anywhere is left out. The spec is very consistent. Numbers, task sizes, the connection budget, timestamp examples, the billing state rules, locking and erasure all check out. What is left is mostly framework-level and frontend detail: 2 medium items and 5 low, none high.

**1. CR-012 says one `@RestControllerAdvice` produces every error, but many errors come from servlet filters (medium)**
- Lines: 105, 692, 1789.
- Quotes: L105 "Every non-2xx response uses exactly the error body below, produced by one `@RestControllerAdvice`". L692 (CMP-002) "request id → JWT validation → CSRF header check → API rate limit → controller → `GlobalExceptionHandler`". L1789 "`api_errors_total{code}`: incremented by `GlobalExceptionHandler`".
- Problem: the 401 (JWT), the 403s (CSRF, missing `USER` role, internal role) and the 429 are raised in servlet filters, before Spring MVC runs. A controller advice never sees them. The spec doesn't say how these responses get the standard error body, or whether they count in `api_errors_total`.
- Fix: route filter errors through one shared `ErrorResponseWriter` (or `HandlerExceptionResolver`) used by the `AuthenticationEntryPoint`, the `AccessDeniedHandler` and the CSRF and rate-limit filters, and have it increment `api_errors_total`.

**2. CORS headers on filter-generated errors are not specified, and CMP-002 leaves CORS out of the filter order (medium)**
- Lines: 137, 692, 63.
- Quotes: L137 "An `OPTIONS` preflight is answered by the CORS filter before the token, CSRF and rate-limit checks". L692 lists no CORS filter. L137 test "foreign Origin → no CORS headers".
- Problem: CR-035 (L63) requires the browser to read `error.code` of a 401, and the 429 needs `Retry-After` exposed. Both only work if the 401/403/429 responses written by later filters also carry `Access-Control-Allow-Origin` and `Allow-Credentials`. If a builder uses Spring MVC's `CorsRegistry` instead, the 401 is unreadable and the login redirect never happens.
- Also unstated: what a request with a foreign `Origin` returns. Spring's default is a 403 with a plain-text "Invalid CORS request", which breaks CR-012's error body.
- Fix: put the CORS filter first in CMP-002 (before the request id filter). State that it adds CORS headers to every response, errors included, and that a foreign `Origin` gets the normal response with no CORS headers, not a 403.

**3. Section 3.4 claims to be the "single source of every UI text", but many texts are missing (low)**
- Lines: 520, 393, 297–302, 420.
- Quotes: L520 "3.4 is the single source of every UI text". L393 (FR-024 c6) has hard-coded Checkout literals `name` "SurfingBear Resume Pro" and `description` "₹299 per month", with no 3.4 key. L420 "score gauge has a text alternative", with no key.
- No keys exist for:
  - the upload control (button and label);
  - the role and level picker labels and its start button;
  - page titles and section headings on the result, history, compare, privacy and Pro pages;
  - the history status, role and resume filter labels and table columns;
  - the score gauge's text alternative;
  - the confirmation shown after erasure or consent withdrawal.
- Fix: add `messages/en.json` keys for these, and keys for the Checkout `name`/`description`, with the price taken from API-017.

**4. The worked examples contradict the FR-009 score formula (low)**
- Lines: 2784–2794 (API-008), 3180–3201 (API-021), against L378.
- Quote: API-008 has `"overallScore": 68, "scoreBand": "FAIR"` with dimensions 72/60/55/90/80/70. FR-009 (L378) gives `round(Σ(score×weight)/100)`.
- Problem: with the weights 25/20/15/15/15/10 those dimensions give 7075/100 → 71, band GOOD. In API-021 the `to` side (80/75/70/90/80/68) gives 78, not 77, and `overallScoreDelta` would be 7, not 9. Contract tests written from these examples would fail.
- Fix: correct the examples (71 GOOD, 78, delta 7), or change the dimension values so they produce 68 and 77.

**5. The `APP_ENV` value for integration tests is not specified (low)**
- Lines: 1394, 1240, 62, 1433, 1217, 1385.
- Quotes: L1394 `APP_ENV` "none (required) … any other value → the task refuses to start". L1240 the JUnit extension "starts the Spring context in `api` or `worker` mode connected as `ro_app`". L62 only `LocalLoginIT` (profile `local`) and `LocalLoginAbsentIT` (profile `dev`) name a profile.
- Problem: every other integration test must pick one of the four environments.
  - `local` turns on the `@Profile("local")` key-pair creation and the fake billing and AI defaults.
  - `dev` turns on the CloudWatch `PutMetricData` call from the sweeper, because `cloudwatch-enabled` defaults to `true` (L1433).
  - The fake guards depend on the choice too (L1217, L1385).
- Fix: state the test value, for example `APP_ENV=dev` with `CLOUDWATCH_METRICS_ENABLED=false`, Razorpay and Anthropic URLs pointed at WireMock and JWKS served by WireMock.

**6. Order of the first migration in a new environment (low)**
- Lines: 1724, 1726, 1728–1734, 1686.
- Quotes: L1724 the services start on `initial_image_sha` "(an image already in ECR)". L1686 "the migration task … creates the login role … `ro_app`".
- Problem: the third-pass `terraform apply` creates `ro-api` and `ro-worker` before any migration has run, so `ro_app` and the schema don't exist yet. The tasks crash-loop, and in prod the `ApiUnavailable` alert pages, until a deploy workflow runs. None of the manual steps 1–5 says to run the migration first.
- Fix: add a runbook step. Either run the migration once (or a `deploy` with `initial_image_sha`) right after the full apply, or create the services with `desired_count = 0` until the first deploy.

**7. Frontend navigation, paging and the status filter are not specified (low)**
- Lines: 297, 298, 395, 442, 63.
- Quotes: L298 "`/analyses` (history) | Paginated list". L395 (FR-026 c6) filter options from "the history items loaded so far". L297 "Your resumes" list uses API-005, which is paginated. L442 "users never leave the platform's navigation".
- Problems:
  - Nothing says how the user moves between `/`, `/analyses`, `/pro` and `/privacy`.
  - The paging style isn't given: page links, or "load more" (which FR-026 c6 implies).
  - It isn't said whether "Your resumes" and the Pro resume filter load every page of API-005 or only the first 20.
  - It isn't said whether FREE users get a status filter control. The CR-035 Playwright test opens `/analyses?status=COMPLETED`, which implies the page reads `status` from the URL.
  - Whether "Withdraw consent" shows when the user has not accepted is not specified.
- Fix: add one paragraph to the 2.2 page table covering all of these.

**Total: 7 items (0 high, 2 medium, 5 low).**
