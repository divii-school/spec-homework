## Final report

Build test of `sachin/spec.md` (v0.8). I read all 3,220 lines and no other file, and edited nothing.

I walked the whole build: the V1–V3 migrations and TBL-001–019, API-001–022 with the check orders and the error list, the worker, sweeper and AI call, Razorpay (checkout, verification, webhooks, reconciliation, the cancel-retry job), the frontend screens and runtime config, the configuration for local/dev/staging/prod, the pipeline, Terraform and observability. Almost everything is pinned down. Below are only the places where a builder would still have to guess or choose between two texts, ordered by impact.

1. **CONTRADICTION: when a TBL-019 row is "done"** (TBL-019 note and 5.4, against 4.3.6).
   - TBL-019 says: "The row is deleted when Razorpay confirms the cancellation, or when a fetch shows the subscription is already `cancelled`, `completed` or `expired` (4.4)". 5.4 says only "deleted when Razorpay confirms".
   - The 4.3.6 outcome table also treats `halted`, `created` past `expire_by`, and HTTP 404 as "done".
   - Impact: a job built from TBL-019 would retry every `HALTED`-reason row forever, which pages `RazorpayCancellationOverdue` as critical.
   - Fix: replace the TBL-019 and 5.4 sentences with "deleted on any 'done' outcome of 4.3.6".

2. **CONTRADICTION / GUESS: how Razorpay says "no such subscription"** (4.4 `FakeRazorpayClient`, against FR-024 c3, FR-029 c8 and 4.3.6).
   - The fake says "Ids it never created → HTTP 400, as Razorpay would."
   - Every decision rule keys "Razorpay holds no such subscription" on HTTP 404. A non-404 4xx on a fetch is not defined in the expiry fetch of FR-024 c3 or in reconciliation. The "fetch fails" row of 4.3.6 covers only timeout, connection and 5xx.
   - Locally, `api` and `worker` run as separate JVMs, each with its own in-memory fake. The worker's reconciliation and cancel-retry therefore get 400 for every subscription the API created.
   - Fix: state the real unknown-id response and map it (and other 4xx) explicitly in all three tables. Make the fake shared (for example DB-backed), or have it answer unknown ids as `created`.

3. **GUESS: erasure racing an upload or analysis start** (4.3.1, 4.3.2, 4.3.6).
   - Erasure takes "per-user advisory lock (same key as 4.3.8)". Upload checks consent, then later does "INSERT resume + resume_text (one transaction)" and takes no lock.
   - An upload that passes its consent check just before an erasure commits stores a resume and S3 object after the user asked for everything to be deleted.
   - Fix: take the same advisory lock in the upload insert transaction and the start-analysis transaction, and re-check consent inside it.

4. **CONTRADICTION: what verification (API-018) writes for statuses other than `active`.**
   - FR-024 c8: "Any other status, or a failed fetch → 202 with the stored state; access then comes from the webhook".
   - The subscription state note says "any non-terminal status may move to the status an applied event, verification or reconciliation reports". FR-029 c5/c9 also have verification "apply a status change" and react to `authenticated`/`pending`.
   - Open question: does verification set `AUTHENTICATED`/`PENDING`/`HALTED` (with a TBL-019 row), or only `ACTIVE` plus the ORPHANED backstop?
   - Fix: list per fetched status what verification writes.

5. **GUESS: who sets `erasure_record.completed_at`** (4.3.6, TBL-011).
   - Only the retry job sets it: "when no rows remain for an erasure_record: set completed_at". That job only reads due `storage_deletion` rows.
   - If the after-commit S3 deletes all succeed, or the user had no files, nothing ever sets `completed_at`.
   - Fix: the after-commit listener sets `completed_at` when its last key is deleted, and the erasure sets it at commit when there are no keys.

6. **GUESS: ShedLock lock durations** (CMP-012/015/016/021, 4.3.4, 4.3.7, FR-029 c8).
   - Every job is "`@Scheduled` + ShedLock", but no `lockAtMostFor` / `lockAtLeastFor` is given.
   - Retention (batches of 500) and reconciliation (one 10 s-timeout Razorpay call per open row) can run long. Too short a lock lets two workers run the same job; too long blocks it after a crash.
   - Fix: add both values per lock name to 4.7.

7. **CONTRADICTION: which PagerDuty integration** (4.8.5 step 5, against 4.8.7).
   - 4.8.5: "PagerDuty service … with its Amazon SNS integration, whose URL goes into … `pagerduty_endpoint`".
   - 4.8.7: "HTTPS subscription to its Amazon CloudWatch integration URL (`pagerduty_endpoint`)", which must also accept the alert manager's plain-text messages.
   - Fix: name one integration type that accepts both CloudWatch alarm JSON and the plain-text Prometheus alerts.

8. **GUESS: where "Continue payment" gets the Razorpay key** (FR-030 c3 state (d)).
   - State (d): "'Continue payment', which reopens Checkout with the same subscription id".
   - The subscription view (API-019) has no `razorpayKeyId`, and the web runtime config (CR-036) does not carry it. Only API-017 returns it.
   - Fix: say "Continue payment" calls API-017 (200, same row) to get `razorpayKeyId`, or add `razorpayKeyId` to the subscription view.

9. **CONTRADICTION: upload check order** (4.3.1, against API-004 and CMP-006).
   - 4.3.1: "(6) magic bytes, (6a) a free extractor slot, (7) protection".
   - API-004 lists "(5) magic bytes; (6) protection …" with no slot step, even though "section 6 wins".
   - CMP-006, which detects magic bytes, runs on the bounded pool. So it is unclear whether a busy server answers a PNG with 415 or 503.
   - Fix: add (6a) to API-004 and state that magic-byte sniffing runs before a pool slot is taken.

Total: 9 (5 contradictions, 4 guesses).
