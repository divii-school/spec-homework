**1. FR-006 c6 / 4.3.2 / 4.7 / 4.8.2: which service sets `prompt_version`?** (medium)
- Lines: 375, 803, 1261, 1409, 1541, 2091.
- The API writes it at insert time: `INSERT INTO analysis (... prompt_version :pv ...)` (803).
- But `ANTHROPIC_PROMPT_VERSION` is set only for the worker: "`ANTHROPIC_PROMPT_VERSION` | wrk" (1541). And it is the worker that loads the file: "a worker whose file is missing refuses to start" (1261).
- If ops change the variable on the worker only, every stored `prompt_version` is wrong. During a rolling deploy the two services can also disagree.
- Fix: the worker writes `prompt_version` on QUEUED→RUNNING; alternatively, set the variable on both api and wrk and validate it in both.

**2. 4.3.8 / 4.3.9 / FR-029 c8: is a same-status update (ACTIVE→ACTIVE with new cycle dates) a "status change"?** (medium)
- Lines: 398, 1033, 1098, 1100, 1104, 3306.
- 4.3.8 says "last_event_at = fetch time **if the status changed**" (1033). FR-029 c8 says "Each row changed counts in `billing_reconciliation_fixes_total`" (398). The test at 3306 says "missed `charged` fixed from `active` … `last_event_at` = fetch time".
- For a missed renewal the row stays ACTIVE. It is undefined whether the cycle dates and `last_event_at` are written and whether the fix counter fires.
- If `last_event_at` is not written, a stale `pending` event can later flip the row to PENDING, and the Pro page then shows state (a) with an immediate cancel.
- Fix: say that "applied" means any change to status, current_start or current_end. Each applied update sets `last_event_at` and counts as a fix.

**3. Section 4 intro vs 4.7 / 4.8.2 / 4.8.4: which variables each APP_MODE validates.** (medium)
- Lines: 592, 1401, 1508, 1524, 1563–1564, 1657.
- Line 592 says "Each mode validates at startup exactly the variables whose 4.8.2 row names its service, and refuses to start if one is missing".
- But many such rows are "default"/"not set", for example `UPLOAD_MAX_BYTES`, and locally `JAVA_TOOL_OPTIONS` and `OTEL_SERVICE_NAME`. Read literally, local start fails.
- 4.8.4 (1657) lists the migrate requirements without `DB_POOL_SIZE`, yet 4.7 marks it "none (required)" (1401) and the 4.8.2 row includes mig (1524).
- Fix: validate only the properties 4.7 marks required, scoped by the service list in each row, and state whether `DB_POOL_SIZE` is required in migrate.

**4. 4.3.6 vs 4.3.9 / TBL-019: the erasure insert can hit the unique key.** (low)
- Lines: 937, 1093, 1098, 2275.
- The erasure does a plain "INSERT subscription_cancellation (ERASURE, erasure_record_id) per subscription in CREATED…PENDING" (937) under `uq_subscription_cancellation_razorpay_subscription_id` (2275).
- A `halted` event whose status change is skipped still inserts a HALTED row "whenever the event names a known subscription" (1098), and the subscription stays open.
- The erasure then fails with 500. If it is changed to ON CONFLICT instead, `erasure_record_id` is never linked.
- Fix: upsert on conflict and set `erasure_record_id` (and reason ERASURE) on the existing row.

**5. 4.8.3 vs 4.8.5 step 3: format of the origin secret.** (low)
- Lines: 1613, 1703.
- One says "`<64 random hex characters>`" (1613); the other says "for the rest, random values of 32 characters from `[A-Za-z0-9]`" (1703).
- Fix: name `web-origin-verify` explicitly in step 3 with a single format.

**6. 4.4 FakeRazorpayClient vs CMP-019: the fake cannot tell which caller fetched.** (low)
- Lines: 696, 1202.
- The fake returns "`created` until the first verification fetch (API-018) for that id". But the client interface is only "create, fetch and cancel" (696), and the same fetch is used by reconciliation and by the expiry fetch.
- Fix: switch to `active` on the first fetch after the API-018 signature passes, through an explicit fake-only hook or a caller parameter.

**7. FR-013 c4 / 4.7: the 150 s fast-poll window has no start point.** (low)
- Lines: 382, 1448.
- Only the give-up timer is anchored: `POLL_GIVE_UP_MS` "counted from `createdAt`". It is not said whether `POLL_FAST_WINDOW_MS` (150000) runs from page load or from `createdAt`, which matters when an older analysis is reopened.
- Fix: state "from `createdAt`" (or "from page load") for the fast window too.

**8. CR-037 / 4.8.3: the CSP applies to every HTML response, including `next dev`.** (low)
- Lines: 145, 1601, 1619.
- `script-src 'self' 'nonce-…'` has no `'unsafe-eval'`, which `next dev`'s hot reload needs. The local run ("`npm run dev`", 1512) would break.
- Fix: allow `'unsafe-eval'` when `APP_ENV=local` and NODE_ENV is development.

**9. 3.4 claims to be "the single source of every UI text", but many texts have no key.** (low)
- Lines: 520, 293, 302, 388, 395, 1204.
- Missing keys include:
  - the FR-019 c8 line "Your Resume Pro subscription ends now and the rest of this month is not refunded" (388)
  - the delete and withdraw confirm dialogs (293, 302)
  - the "Download PDF", "Analyse", "Compare" and "Simulate payment" buttons
  - the FR-026 c6 labels "Uploaded …" and "Expired resume, analysed …"
- Fix: add these keys to 3.4.

**10. 4.8.3 / 4.8.5: security groups are given only for ro-api and the ALBs.** (low)
- Lines: 1608–1611, 1676–1678, 1742.
- There are no ingress rules for RDS 5432, Redis 6379, ro-web 3000 or ro-worker.
- Fix: add one SG table: RDS and Redis from the ro-api, ro-worker and ro-migrate SGs only; ro-web 3000 from the public ALB only.

**11. 4.5 / 4.8.4 / section 5: how integration tests get a schema is not said.** (low)
- Lines: 1225, 1657, 1869.
- `spring.flyway.enabled=false` applies in api and worker, and V1 ends with `GRANT … TO ro_app`, so the `ro_app` role must already exist. Testcontainers ITs therefore need a defined bootstrap.
- Fix: say that ITs run the migrate-mode logic (create `ro_app`, then Flyway) against the container before the context starts.

**12. 4.8.4 Playwright stack in the web repo: no bucket creation.** (low)
- Lines: 1512, 1594, 1663.
- `sb-ro-local` is "created by the LocalStack init script", but that script lives in the API repo's compose. The web repo's `e2e/docker-compose.yml` is not told to create the bucket.
- Fix: the web repo's `e2e/docker-compose.yml` mounts the same `10-bucket.sh` init script.

**13. CMP-010 / 4.3.3: unexpected non-AI errors in the worker are not covered.** (low)
- Lines: 687, 853–871, 1720.
- Only AI failures are mapped to FAILED. A DB exception, missing `resume_text` or bug leaves it unspecified whether to XACK, mark FAILED (and with which reason, since the CHECK allows only three) or leave the row RUNNING for the sweeper.
- Fix: catch everything, leave the row RUNNING, XACK, and let the sweeper fail it as `AI_TIMEOUT` with ERROR `analysis.worker_error`. Or add a reason value.
